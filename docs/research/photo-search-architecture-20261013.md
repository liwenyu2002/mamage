# MaMage 检索优化：先验证现成方案，再替换生产检索

核验日期：2026-10-13。本文区分官方能力、当前代码事实和拟采用设计；不是已完成的上线说明。此前新闻稿工作区改动保持原样。

## 结论

有可复用的开源图文模型和检索组件，但没有已核实的单个模型能同时保证组织权限、熟人身份、人物衣着归属、否定条件和低延迟。应复用模型，保留业务约束，建立统一评测，而不是继续为每种衣服增加字符串规则。

建议的整体路线：

```text
用户查询
  -> 当前小组与相册访问范围
  -> 查询理解：人物 / 日期 / 相册 / 媒体类型 / 否定 / 视觉意图
  -> 不可自动删除的明确约束
  -> 关键词 + 整图图文向量 + 人物区域向量，分别召回
  -> 合并排名
  -> 只对靠前候选做图文精排与人物区域核对
  -> 再次验证权限、身份与否定约束
  -> 严格匹配 / 明确标注的相关候选 / 无结果
```

这是面向 MaMage 的设计，不声称复现了 Google 或 Apple 未公开的内部架构。

## 1. 当前代码事实

- `apps/server/lib/ai_photo_search.js` 用文本大模型把句子转换为字段。它不查看候选照片。
- `apps/server/lib/photo_search.js` 主要用 SQL LIKE 匹配描述、标签、OCR 等，再关联人物档案。
- 当前零结果重查会删除内容条件，甚至删除单人条件；没有可靠主体时可能返回整个授权小组的图库。这不是语义理解成功。
- 人物与衣着目前在照片级交集，不能证明某件衣服属于指定人物。
- `apps/server/lib/image_similarity.js` 与 `scripts/resnet_feature.py` 提取 ResNet-50 图片特征，用于图像间相似度。没有配对的文本编码器，不能直接承担中文到图片的检索。
- 2026-10-13 的18次生产只读请求用于定位行为与耗时，原始记录保留在忽略的 `.local/search-audit-20261013.json`。这不是人工标注的准确率基准，也不应推送原始人物记录。

## 2. 可复用的成熟机制

### 产品对照

- Google Photos 官方支持已命名人物与动作描述组合；Ask Photos 另外提供更复杂的问题理解与检索。
- Apple Photos 官方明确给出“某人穿某种衣服做某动作”的自然语言搜索示例，但没有公开校园合影的属性归属准确率。
- Immich 的可核验实现将后台图片编码、在线文本编码和结构化人物过滤分开，不依赖描述字段含有同一关键词。

产品能力和已公开实现应分开阅读，完整核验见同目录的 `photo-search-products-20261013.md`。来源：[Google 搜索帮助](https://support.google.com/photos/answer/15235862?hl=en)、[Apple 搜索帮助](https://support.apple.com/guide/iphone/search-for-photos-and-videos-iph392d77d5f/ios)、[Immich 搜索](https://docs.immich.app/features/searching/)

### 混合召回与精排

Elastic 官方将关键词与向量查询合并成一份排名，并推荐 RRF；其排名文档将精排放在候选召回之后。这支持“先找候选，再精排”的工程路线，不意味着必须给 MaMage 部署整套 Elasticsearch。[混合检索](https://www.elastic.co/docs/solutions/search/hybrid-search)、[排名与精排](https://www.elastic.co/docs/solutions/search/ranking)、[RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

RRF 解决不同召回分数不在一个尺度的问题，不负责保证身份、否定或衣着归属；这些不能被排名积分抵消。

### 同一主体上的多个条件

Qdrant 官方明确提示：数组中两个普通过滤条件可能分别匹配两个不同对象；需要 nested 条件才能保证它们命中同一个对象。这和“同一张照片里两个人，红衣属于另一个人”的错误结构相似。[过滤设计](https://qdrant.tech/documentation/search-patterns/vector-search-filtering/)、[nested 过滤](https://qdrant.tech/documentation/search/filtering/)

采用这一结构前必须先生成可靠的人物区域数据。增加 nested 字段本身不会识别衣服，也不会自动把脸绑定到身体。

### 权限与检索范围

先确定允许搜索的范围，并在召回过程中限制该范围；不应全局取 top-k 后才删除不可见结果。候选返回前仍需通过现有数据库权限复核，处理分享到期、用户换组和资源删除。

向量后端只是派生索引，MySQL 仍是权限与资产归属的权威来源。当前阶段无需迁移业务数据库。

## 3. 现成模型候选

| 候选 | 官方明确用途 | 在本项目中的定位 | 待实测事项 |
|---|---|---|---|
| Chinese-CLIP ViT-B/16 | 中文图文检索，188M 参数，仓库标注 MIT | 轻量基线，验证是否足够快、足够准 | 中文动作/衣着组合、长句、MPS/CPU、内存 |
| Qwen3-VL-Embedding-2B | 图文/视频等统一向量，支持中文，2B，Apache-2.0 | 较新的多模态召回对照组 | Mac 运行兼容性、文本编码耗时、批量索引吞吐 |
| Qwen3-VL-Reranker-2B | 查询与候选成对输入并输出相关性 | 只对少量候选精排，不全库逐图调用 | 每批候选耗时、否定与主体绑定是否改善 |
| SigLIP 2 | 多语言图文编码、图文检索，官方权重 Apache-2.0 | 可选第三组，不作为未经测试的默认赢家 | 中文校园场景、目标 checkpoint 的实际大小与速度 |

来源：[Chinese-CLIP 官方仓库](https://github.com/OFA-Sys/Chinese-CLIP)、[官方部署说明](https://github.com/OFA-Sys/Chinese-CLIP/blob/master/deployment.md)、[Qwen3-VL-Embedding-2B](https://huggingface.co/Qwen/Qwen3-VL-Embedding-2B)、[Qwen3-VL-Reranker-2B](https://huggingface.co/Qwen/Qwen3-VL-Reranker-2B)、[Qwen 官方代码](https://github.com/QwenLM/Qwen3-VL-Embedding)、[Google SigLIP 2 权重](https://huggingface.co/google/siglip2-base-patch16-224)

注意：Qwen 文档中的向量量化不等于保证模型权重低比特推理已在 Mac 上验证。公开基准也不能换算成本校图库的准确率或耗时。通用文本 embedding 不能直接与现有 ResNet 或人脸向量比较；不同模型版本的向量不得混用。

推荐先跑 Chinese-CLIP 和 Qwen3-VL-Embedding 两组，暂不同时常驻多个大模型。精排是否常驻、是否换用更轻模型，应由真实延迟和收益决定。

## 4. 主体绑定的数据设计

保留两种不同粒度的索引：

- 照片级：photoId、modelVersion、图像向量、文本向量、OCR、相册、环节、时间、组织与小组范围。
- 人物实例级：photoId、faceId、personId、身体区域、face-to-body 关联置信度、区域向量、衣着/动作属性及各自证据与版本。

“某老师穿红衣”要求先关联该老师的人脸与身体区域，再判断区域内衣着。不能简单把人脸框向下拉长就当成身体框；遮挡、坐姿、合影和人脸交叉都需要低置信度拒绝或回退。

索引时可以用现成行人检测/视觉定位模型配合已有脸框，再做几何与一对一关联。具体检测模型尚未选型和实测，不在本轮宣称已解决。

“未知”不等于“不符合”。衣着/动作没有可靠证据时，应该显示相关候选或待确认，而不是算作已满足或已排除。

## 5. 查询约束约定

不可在零结果时自动删除：组织/小组权限、明确人物、多人同框、单人要求、明确日期、指定相册、媒体类型、否定条件。

模型只提供有来源的查询解释，不能生成任意 SQL。人名应与当前授权人物库核对，支持长句；解析失败后应保留已经可靠识别的实体，不把失败写成“AI 已理解”。

视觉语义适合相似度排序，但“不要红衣”“没有其他人”等排除不能只通过向量远近推断。需要可验证的属性、局部核对或明确的未知状态。

零结果时分层返回：

1. 严格匹配为空，明确显示为空。
2. 有可靠主体时可提供单独的“相关候选”，保留主体和所有权限，说明未确认的视觉条件。
3. 需要用户选择才能真正放宽明确条件，不能悄悄把全部图库作为搜索命中。

## 6. 性能设计

- 上传后后台批量计算图片与人物区域向量，版本化、可恢复、低优先级回填；搜索时不重新分析全库照片。
- 模型进程常驻，限制图像批量大小与并发；不沿用每张图片启动一次 Python 的方式。
- 查询阶段主要编码短文本、检索向量，重模型只处理少量候选。
- 文本向量缓存和受权限约束的结果缓存分开。结果缓存包含用户/小组/权限版本、索引版本，不能跨组复用候选列表。
- 初期针对小规模授权范围可以比较 NumPy 精确矩阵检索与 ANN。是否引入独立 Qdrant 由规模、过滤需求、延迟和运维成本决定，不默认增加新数据库。
- 50000 张照片、每张512维 float32 的原始向量约97.7 MiB，仅为矩阵估算，不包括模型、区域副本、元数据及索引。

## 7. 固定验收，而不是案例驱动补丁

先确定300至500张授权照片作为固定语料，覆盖相似连拍、同框、服装换色、红色背景但非红衣、讲台旁站立但未发言、遮挡等难负例。人脸不准的样本要单独标记，避免把身份错误算成检索模型错误。

构建至少50条人工标注查询，按以下类别报告，不只看总体平均：

- 已知/不存在人物，单人/多人同框。
- 人物+颜色/衣着/动作，属性属于其他人的困难负例。
- 同义问法、礼貌长句、口语、错别字。
- 排除条件、日期/媒体类型/相册范围。
- 确实不存在的场景，AI超时、未索引照片、权限拒绝。

对照：现有SQL+LLM、轻量图文模型、Qwen多模态召回、最优召回+候选精排。

记录 Precision@10、Recall@50、nDCG@10、硬约束违规、无结果误报、冷/热 p50/p95、索引耗时、峰值内存。身份、权限和明确排除违规要求为零；其他效果与延迟目标在实测基线后确定，不提前保证。

工具已提供：

```bash
node apps/server/scripts/evaluate_photo_search.js judgments.json results.json report.json
node apps/server/scripts/test_photo_search_evaluation.js
```

`photo-search-evaluation.example.json` 只是合成格式示例。成绩只有在固定语料全部人工标注且输出未超出该语料时才计算；没有人工标签的结果不冒充准确率。Precision@10 固定以10为分母，少于10张的查询需结合 Recall@50 与分组结果阅读。

## 8. 发布顺序

1. 完成官方产品调研、固定评测语料与查询约束约定。本轮只落地调研和评测工具。
2. 隔离测试现成模型，测资源、速度、准确性与主体绑定；不开启生产全量回填。
3. 实现独立、可替换的检索内部模块，旧接口不变，保留原链路作为对照。
4. 影子请求比较，不改变用户结果；人工检查失败类别。
5. 小组灰度、后台增量索引、可回退上线。索引或模型异常时保留权限和明确条件，不退到全库。

以上是升级前的调研与基线。以下记录同日后续实施，不将只读冒烟结果当作人工标注的准确率。

## 9. 首轮主链升级

本地代码已实现，尚未提交、推送或切换生产服务：

- 当前组织人物库按完整查询发现实际提及的姓名，支持长句；模型编造的人名不能替换原文人物。摄影师与被摄人物分开，排除人物使用独立的人脸否定条件。
- 内容概念组内 OR、组间 AND，支持模型提供的等义表达和一小组保守词典。不把麦克风等相关道具当成“正在发言”的等义条件。
- 单人、同框、日期、媒体类型、质量和否定条件不因零结果被自动删除。截止日期包含当天全部时间。
- `related=1` 仅在有明确且已解析的人物时允许主动查看相关候选，只放宽正向内容条件；身份不完整、没有人脸权限、纯场景无命中时不允许全库回退。返回 `search.matchType`、`relatedAvailable`、`notice` 供前端统一展示。
- 可完整本地解释的常见人物组合不调用大模型；其他查询仍走 AI。解析请求合并、缓存包含端点与北京时间日期、上游超时取消、并发上限默认4。空结果只做计数，不查询和签名图片列表。
- 首页与相册内显示统一的严格匹配/相关候选状态；清空或修改搜索时取消旧请求，避免旧结果重新覆盖当前界面。
- 前一轮搜索日志同步支持等义词组与排除人物，继续脱敏并按组织导出。

已完成隔离契约测试、全项目回归与构建。对生产数据的诊断通过独立内存模块进行，仅允许 SELECT，不启动日志、后台任务或数据库迁移，也不替换运行中的文件。样例人物单人照约77ms，红衣服组合约42ms、长句约44ms、排除红衣服约39ms；这是单轮服务端耗时，不是网络端到端 p95 或准确率承诺。

边界仍然存在：本轮没有接入图文向量模型或人物身体区域索引。多人照片中，衣着/动作属于哪一位仍无法从整图标签证明；前端明确提示需要核对。视觉模型对照评测与主体绑定仍按前述路线推进，不将关键词升级包装成已完成的多模态检索。

## 10. 渐进展示与检索动效

同日后续本地实现，尚未部署。`GET /api/photos/search?stream=1` 在完成权限检查后返回 NDJSON，事件为 `status`、`results`、`complete` 和安全的 `error`，15秒空闲心跳防止连接无反馈。旧 JSON 调用不变；新前端遇到尚未升级的 JSON 后端也可兼容。

先确认查询条件，再读首批8张，随后最多每批64张，沿用单页200张上限，最后统计总数。第一批不等待 COUNT；未完成时总数为 null，不显示虚构百分比。复杂查询仍要先完成 AI 条件理解，不能为了早出结果把未满足人物、日期、否定等条件的候选冒充严格结果。没有实现 AI 解析前的未验证结果预览。

首页和相册内共用阶段状态条及轻量骨架，新增照片淡入，统计期间已显示照片仍可打开。相册内搜索临时用网格按相关性展示，退出搜索恢复原布局。图片尺寸占位稳定，动画只用透明度与位移；支持减少动态效果。相册结果位于照片结果之后，避免晚到的相册卡片把正在看的照片往下顶。

换词、清空和关闭请求会中止读取并通知后端停止后续批次与计数；已经在执行的 MySQL 查询不做强制杀连接。断流保留已显示照片并提示未完成，不重试后悄悄扩展结果，也不将多帧重复记作多次搜索。服务端在每次阶段输出与后续查询前检查取消状态，并处理写入背压。

测试包含：首批早于被阻塞的最终结果、中文跨字节分块、单次计数、授权先于流式头、组织与人物条件保留、客户端断开、旧 JSON 兼容、异常帧和有界缓冲。真实相册模块的隔离预览还验证了统计未结束即可打开大图，以及换词取消旧请求；未对生产服务和代理做切换。
